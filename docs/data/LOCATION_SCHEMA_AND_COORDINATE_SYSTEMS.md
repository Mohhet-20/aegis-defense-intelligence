# Location Schema and Coordinate Systems (Phase 7)

**Status: IMPLEMENTED.**

## 1. One mixin, four tables, zero new location tables

`app/models/mixins.py::GeoLocationMixin` is the single shared definition
of "a location" in this codebase. `Event`, `Asset`, `Sensor`, and
`Observation` already had `latitude`/`longitude` since Phase 1; Phase 7
extends the *same mixin* with 7 new columns, applied identically to all
four tables by one Alembic migration
(`alembic/versions/7cafe0cb4340_phase7_geospatial_intelligence.py`, 28
`ADD COLUMN` statements, autogenerated cleanly with no hand-fixes
needed). A separate `locations` table with a foreign key was
deliberately rejected -- see
`docs/architecture/GEOSPATIAL_INTELLIGENCE_ARCHITECTURE.md` Section 3B
for the reasoning.

| Column | Type | Nullable | Meaning |
|---|---|---|---|
| `latitude` | float | yes | WGS84 decimal degrees, -90..90. `None` = no location, never `0.0`. (Phase 1) |
| `longitude` | float | yes | WGS84 decimal degrees, -180..180. Same null discipline. (Phase 1) |
| `coordinate_reference_system` | string(20) | **no**, default `"WGS84"` | Stated, not assumed -- see Section 2. |
| `location_origin` | string(20) | yes | One of `LOCATION_ORIGINS`: `source_reported`, `validated`, `derived`, `estimated`, `inferred`. See Section 3. |
| `location_validation_status` | string(20) | yes | One of `LOCATION_VALIDATION_STATUSES` (`valid`/`invalid_range`/`non_finite`/`unsupported_crs`) -- but see `docs/data/LOCATION_PROVENANCE_AND_UNCERTAINTY.md` for why this stored column is NOT what query/quality endpoints actually read. |
| `location_uncertainty_m` | float | yes | Positional uncertainty radius in meters. `None` = unknown, never 0. |
| `altitude_m` | float | yes | Optional altitude. |
| `altitude_reference` | string(20) | yes | One of `ALTITUDE_REFERENCES`: `wgs84_ellipsoid`, `msl`, `agl`. |
| `location_provenance_note` | string(300) | yes | Short human-readable note (e.g. "seed script, synthetic_demo"); never a place for secrets/PII. |

## 2. Coordinate reference system: stated, not assumed

`SUPPORTED_COORDINATE_REFERENCE_SYSTEMS = ("WGS84",)` -- the only CRS
any real connector, ingestion adapter, or seed script in this codebase
has ever produced. `coordinate_reference_system` defaults to `"WGS84"`
at the column level (so every pre-Phase-7 row and every row inserted
through an unmodified write path is correctly backfilled/defaulted)
but is a real, settable field: a record whose `coordinate_reference_system`
is set to anything else (e.g. a UTM zone string) is classified
`unsupported_crs` by `app/geo/validation.py` and is **never** plotted,
distance-calculated, or included in a spatial query result until a
documented conversion exists. No conversion pipeline exists today
because nothing in this project has ever needed one -- this is an
honest gap, not a silently-assumed WGS84 passthrough. The seed script's
own `unsupported_crs` demonstration row (`scripts/seed.py`) exists
specifically to exercise this path end to end against real seeded
data.

**Validation check ordering (load-bearing for anyone adding a demo
row):** `app/geo/validation.py::validate_coordinates()` checks
`invalid_range` **before** `unsupported_crs`. A row meant to
demonstrate `unsupported_crs` must therefore use in-range-looking
lat/lon values (e.g. `38.90, -77.03`) with a non-WGS84
`coordinate_reference_system` string -- realistic UTM easting/northing
numbers (six-digit meter values) will trip `invalid_range` first and
never reach the CRS check. This was discovered via live
Playwright/screenshot verification of the Location Quality Center
during this phase and fixed in `scripts/seed.py`; see
`docs/implementation/history/PHASE_7_FINAL_REPORT.md`.

## 3. `location_origin`: vocabulary exists ahead of the capability

`LOCATION_ORIGINS = ("source_reported", "validated", "derived", "estimated", "inferred")`.
Phase 7 writes `source_reported` for seeded/connector-supplied
coordinates and leaves `location_origin` `None` on every other write
path (identical to how it behaved before this column existed). The
`derived`/`estimated`/`inferred` values are **reserved vocabulary, not
yet produced by any service** -- nothing in this phase computes a
location from other records (e.g. triangulating a sensor's position
from multiple reports) and backfills one of these three statuses.
Documented here honestly as reserved-but-unused, the same discipline
Phase 6 used for `Permission.SENSOR_QUALITY_REVIEW`.

The map/export marker-category system (`MapExplorerPage.tsx`'s
`categorize()`, `docs/analytics/SPATIAL_TEMPORAL_ANALYTICS.md`) is
built to visually distinguish `validated`/`derived`/
`estimated_inferred`/`uncertain`/`unvalidated`/`synthetic` categories
as the specification's marker taxonomy requires, even though only
`validated` (derived live from `location_validation_status == "valid"`,
never read off the stored column -- see
`docs/data/LOCATION_PROVENANCE_AND_UNCERTAINTY.md`), `unvalidated`,
`uncertain`, and `synthetic` are reachable with today's real data; the
category logic is real and tested, the `derived`/`estimated_inferred`
categories simply have no current data path that would ever populate
them.

## 4. What this does NOT do

- No PostGIS geometry column, no spatial index, no `SRID`-aware column
  type -- plain `Float` columns, queried via bounding-box pre-filter +
  exact haversine check (see
  `docs/architecture/GEOSPATIAL_INTELLIGENCE_ARCHITECTURE.md` Section 4).
- No coordinate-system conversion pipeline (UTM-to-WGS84 or similar) --
  an `unsupported_crs` record's raw numbers are preserved, never
  converted or guessed at.
- No per-row CRS other than `WGS84` has ever been written by real code
  in this project -- `unsupported_crs` only appears via one explicit,
  clearly-labeled seed-data demonstration row.
- No geofencing, polygon, or multi-point shape storage -- every
  location is a single point.
